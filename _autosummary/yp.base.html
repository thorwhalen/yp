class yp.base.CachedPkgNameStub(mapping=None)[source]#

Bases: Mapping

The {pkg_name: pkg_stub} mapping of every project on PyPI, loaded lazily.

Reading the cache is deferred to first use, so import yp stays cheap and, more importantly, never fails because of a missing data file: a missing cache raises MissingPackageNamesError – with an actionable message – only if and when the names are actually needed.

>>> stub = CachedPkgNameStub()
>>> 'numpy' in stub
True
>>> stub['scikit-learn']
'scikit-learn'
>>> len(stub) > 100_000
True

class yp.base.Pypi(*, info_extractor=None, proj_names=None, user=None, strict_getitem=False)[source]#

Bases: KvReader

Get a mapping of all of pypi projects.

>>> p = Pypi()

The keys of this mapping are the project names. There are lots!

>>> len(p)
405120
>>> 'numpy' in p and 'dol' in p
True
>>> 'no_way_this_is_a_package' in p
False

The values of the mapping are the corresponding project’s info, which is a nested dict of good stuff.

>>> info = p['numpy']
>>> {'info', 'last_serial', 'releases', 'urls'}.issubset(info)
True

Tip

To only get the info you want, you’ll

The project info is obtained, live, making requests to the https://pypi.python.org/pypi/{pkg_name}/json API, but the list of all project names is actually taken from a local file. You should update that file regularly (but not TOO regularly!) to be in sync with pypi.org. To do so, do this:

>>> Pypi.refresh_cached_package_names()

If, on the other hand, you don’t want all projects of Pypi to be the collection you’re working with, you can specify what user they should belong to:

>>> p = Pypi(user='thorwhalen1')
>>> len(p)
131

You can also explicitly give Pypi a collection of projects you want to work with:

>>> p = Pypi(proj_names={'numpy', 'pandas', 'dol'})
>>> len(p)
3

You can do a lot more by simply using the tools of dol to change the mapping you want to work with in all kinds of ways!

static live_is_available(pkg_name)[source]#

Check if a package name is available, live (directly on pypi, not a cache). Returns True iff the name is free to register.

Uses the PyPI JSON API as the authoritative signal (404 => free, 200 => taken), which is more reliable than scraping the HTML project page (that can return a soft 200 for non-existent names in some network environments). PyPI normalizes names per PEP 503, so separator/case variants of a taken name correctly report as unavailable.

Update the {pkg_name: pkg_stub} stored data with a fresh call to get_updated_pkg_name_stub.

yp.base.slurp_user_projects_info(user, *, with_details=False, cache_results=True, refresh=False, user_packages=<function xmlrpc_user_packages>, project_json=<function pypi_project_json>, max_workers=8)[source]#

The list of projects that user owns or maintains on PyPI.

Each record has name, href (the project’s PyPI page) and role ('owner' or 'maintainer'). With with_details=True it also has description (the summary), version and date (upload time of the last release), fetched concurrently from the JSON API: one request per project, so expect some seconds for an account with hundreds of projects.

If cache_results is True (the default), results are cached on disk, in slurp_user_projects_info.user_projects_info_cache_folder. If refresh is True, the cache is refreshed. A cache written without details is refetched when details are asked for.

user_packages (user -> [(role, name), ...]) and project_json (name -> dict) are the transports; the defaults call PyPI.

>>> infos = slurp_user_projects_info('thorwhalen1')
>>> sorted(infos[0])
['href', 'name', 'role']
yp.base.xmlrpc_user_packages(user, *, timeout=30)[source]#

[(role, name), ...] for the projects user owns or maintains on PyPI.

Calls PyPI’s XML-RPC user_packages method, the only official way to list an account’s projects (deprecated by PyPI but still answered). The HTML user page (https://pypi.org/user/{user}/) answers scripts with a JavaScript challenge, so it cannot be used.

>>> xmlrpc_user_packages('thorwhalen1')[:2]
[['Owner', 'accompy'], ['Owner', 'aix']]
